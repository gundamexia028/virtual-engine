# PROJECT_CONTEXT.md

## 1. 项目名称

儿科药物性严重过敏反应动态分支虚拟仿真训练引擎。

项目内部可简称：

* 虚拟引擎
* 严重过敏反应虚拟仿真引擎
* 动态分支训练引擎

## 2. 项目性质

本项目是一套面向护理人员和护理专业学生的网页化虚拟仿真训练系统。

系统通过病例情景、动态分支、操作选择、错误反馈、评分、复评和沟通任务，训练使用者识别并处理儿科药物相关严重过敏反应。

本项目属于教学和培训工具，不属于医疗器械，不用于替代真实临床判断、临床诊疗流程或院内抢救制度。

## 3. 项目背景

严重过敏反应起病迅速，可能在短时间内累及皮肤黏膜、呼吸、循环、胃肠道和神经系统。

在实际临床培训中，存在以下问题：

1. 高风险事件发生频率相对较低，部分护理人员缺乏真实处置经验；
2. 传统课堂教学难以完整呈现病情动态变化；
3. 普通题库只能判断答案对错，难以模拟错误操作产生的后果；
4. 线下情景演练组织成本较高，难以频繁重复；
5. 不同学习对象在知识基础、任务能力和临床经验方面差异明显；
6. 培训结果缺少结构化、可追溯的数据记录。

本项目拟通过动态分支病例，使使用者在安全的虚拟环境中反复练习识别、判断、处置、复评和沟通。

## 4. 核心训练目标

系统重点训练以下能力：

1. 识别严重过敏反应的早期表现；
2. 判断呼吸、循环及其他系统受累情况；
3. 及时呼救并启动相应急救流程；
4. 正确进行初始处置；
5. 理解肾上腺素在严重过敏反应急救中的核心地位；
6. 配合气道管理、氧疗、静脉通路、液体复苏及生命支持；
7. 动态复评病情和治疗反应；
8. 识别持续性、双相或难治性严重过敏反应风险；
9. 完成团队协作、信息传递和SBAR沟通；
10. 形成规范化的临床思维和护理行为。

具体医学内容必须以项目指定的指南、专家共识、研究资料和经确认的院内规范为依据。

## 5. 目标使用人群

### 5.1 临床模式

主要面向：

* 在岗临床护士；
* 儿科护理人员；
* 新入职护士；
* 分层培训护士；
* 参与严重过敏反应抢救的相关医务人员。

临床模式强调：

* 快速识别；
* 临床判断；
* 抢救处置；
* 团队协作；
* 动态复评；
* 风险控制；
* 规范记录和沟通。

### 5.2 学院模式

主要面向：

* 高职护理专业学生；
* 本科护理专业学生；
* 实习阶段护生；
* 护理院校教师组织的教学和考核对象。

学院模式与临床模式共享医学核心，但不能机械复制临床模式。

学院模式需要根据护生能力重新设计：

* 角色任务；
* 病例难度；
* 操作数量；
* 按钮措辞；
* 错误反馈；
* 教学提示；
* 评分标准；
* 复盘内容。

学院模式重点评价：

1. 病情识别；
2. 及时呼救；
3. 初始处理；
4. 抢救配合；
5. 病情复评；
6. SBAR及团队沟通。

## 6. 模式设计原则

### 6.1 医学核心一致

临床模式和学院模式的诊断、药物、剂量、给药途径、气道管理、循环支持和复评原则，应建立在相同且经过核实的医学依据上。

### 6.2 教学任务不同

临床人员和护生承担的角色责任不同，因此：

* 不要求护生独立承担超出其学习阶段的临床决策；
* 学院模式应减少不适合学生的高阶任务；
* 学院模式错误分支应具有明确教学意义；
* 临床模式可保留更复杂的病情变化和团队决策。

### 6.3 按钮保持中性

考核场景中的按钮文字不得直接暴露正确答案。

例如，原则上不应使用明显暗示答案的文字：

* “立即正确使用肾上腺素”
* “错误地先使用激素”

应使用接近真实行为的中性措辞，并通过结果和反馈体现行为是否恰当。

### 6.4 错误具有后果

系统不应仅提示“回答错误”，而应根据错误操作呈现合理的病情变化、时间延误、评分影响或教学反馈。

错误后果必须符合医学逻辑，不得为了增加难度而设置不合理结果。

### 6.5 允许复评和纠正

训练模式可以允许使用者在反馈后重新判断或纠正操作。

考核模式是否允许返回、改选或重复操作，应根据正式考核规则确定，并在系统中保持一致。

## 9. 权限与隐私目标

系统需要考虑临床机构与护理院校的使用场景。

原则上：

1. 临床数据与学院数据应进行逻辑区分；
2. 医院管理者只能查看其授权范围内的数据；
3. 学院教师只能查看其授权学院或班级范围内的数据；
4. 普通使用者不得访问管理端数据；
5. 不应向任一普通管理者开放全平台数据；
6. 不得在公开代码中保存真实密钥、密码或访问令牌；
7. 培训数据应尽量减少收集不必要的个人身份信息；
8. 数据导出必须服从权限控制。

具体权限实现必须在代码和后端接管后单独核查。

## 10. 版本管理背景

项目已有连续迭代历史。

已确认的版本管理原则：

1. 主系统版本线连续迭代；
2. 学院模式不另建脱离主系统的独立版本线；
3. 学院模式应作为现有主系统的增强模块；
4. 临床模式在后续学院模式开发中必须保留；
5. 当前实际基线版本必须在导入原始版本包后核实；
6. 未核实代码前，不在本文件写入“当前正式版本”。

版本状态记录在：

* `docs/CURRENT_STATUS.md`
* `docs/VERSION_HISTORY.md`
* `CHANGELOG.md`
